# Alchemy Devtools

It instructs the agents doing decompilation work on Alchemy: matching, measuring, adopting, humanizing the source and writing its docs, and it keeps the history of how the matching was done. Alchemy's own `AGENTS.md` is for people building with Alchemy (changing the game, adding to it, reading it) and keeps L1 to L3, S3, A1 to A6, W1, W3 and W5; every other rule lives here. The rules keep their Alchemy letters and wording, since commits and code cite them; where the two files meet, Alchemy's wins. The agents keep this file current, wording included. Pascal decides compilers, what counts as DONE, and deleting anything that cannot be restored; everything else goes ahead without asking, including fixing a check that wrongly blocks honest work as long as it still refuses everything it refused before.

Evidence is our own cartridge dumps, the project's source and public documentation. Never another project's work on the same game, never leaked SDKs or sources, never a ROM or game file committed or uploaded.

The project builds without Rust; nothing here takes part in a build. Resolve the target checkout at runtime, from the working directory or `ALCHEMY_ROOT`; never bake a path into an executable. `render` runs a built edition in libmgba behind the optional `render` feature and only reads the ROM. Test with `cargo test --locked --workspace` and `ALCHEMY_ROOT` pointing at a bootstrapped checkout, once without the feature and once with it; neither may warn. The reference ROMs the toolkit reads go under the checkout's `roms/` as `tla-ja.gba` and so on, checked against `rom.sha1`, never committed. `README.md` says how to install it.

## The work

Alchemy rebuilds Golden Sun: **The Broken Seal** (☀️, build `tbs`) and **The Lost Age** (⚓️, `tla`) byte for byte from readable C, assembly and editable assets, in Japanese, English, German, Spanish, French and Italian: twelve editions, `tbs-ja` to `tla-it`. Japanese releases are the source editions; localizations are measured differences.

Matching is finished: both games build byte for byte from source, and both reached 100% (the chart in `README.md` is the record of how, no longer updated). The work ahead is the source itself.

### Goal

The aim past DONE is the source itself, as clean, human and minimal as it can be made (Pascal, 12 November 2026). A change that adds a file, a wrapper, a table or a line has to leave the code plainer to read, or it does not go in.

- **DONE** is pret's 100%, never stricter: all six editions of a game build byte-identical from source, verifiable from `rom.sha1`; DONE code and data are both 100% (C2); no function is matched by an assembly body or inline asm beyond the proven `CAMELOT_ASM` helpers; nothing in the build reads a ROM, confirmed by an independent audit (O4); the C compiles with a current GCC (`make modern`); every fake match is tagged and counted (S2). Both games have reached it.
- **Finished** means more: every asset ported (A1), `recon/<game>` gone, no FAKEMATCH device left, a limited set of stock compilers (K1 to K3), every mechanism and scene humanized (H4), and each game linked from one linker script run through the C preprocessor, its editions told apart by the same `LANGUAGE` and patch-level tests as the C, as both games now are (Pascal, 9 November 2026).
- **Released** is where Alchemy turns from decompiling to a platform people build with: Finished, the ROM shiftable (a shift test passes), a playable build that skips the comparison with `BUGFIX` and `UBFIX` documented, both games built in CI from a clean clone without a ROM, the docs covering both games, and an independent leak audit (O4). It is a state of the source: no tag, no published release, and no licence file, as pret's games have none (Pascal, 12 November 2026). The matching method, counting and tooling then live in alchemy-devtools, which Alchemy neither installs nor runs, and Alchemy's `AGENTS.md` is rewritten for people building with it (Pascal, 9 November 2026).
- **Humanized** means the source reads as a Game Boy Advance game a team wrote in C: someone English-speaking at Camelot in 2026 could have written it, and a programmer who opens it cold learns how the game works from it and from the docs written from it (H1). What is left over reads as the exception: "about a hundred odd fake matches, and the rest looks like a real game made by people" (Pascal, 13 November 2026). ☀️ is close; ⚓️ is the work ahead.

### Boundaries

Ask Pascal first: any compiler, option, routing or alchemy-gcc change (K1 to K3); anything that changes what counts (C1 and C2; W6); deleting what cannot be restored; pushing or publishing outside the landing Workflow 4 authorizes.

Never bent: the legal rules (L1 to L3, in Alchemy's `AGENTS.md`), the ROM kept out of the build (O1), and all twelve editions byte-identical (W5, there too).

### Workflow

1. Work on a branch, in the main checkout unless another session shares it, then in a worktree of your own; `main` is the only long-lived branch.
2. `main` is byte-identical in every edition at every commit (W5). A branch need not be: humanizing makes its big moves first and repairs afterwards (Humanizing a game, below), each commit saying whether it matches, and the branch lands only once every edition matches again.
3. A change that moves bytes is repaired forward, in source, until it does not (O4), measured with `alchemy-devtools diff` and `passdiff`; it is never undone by restoring the old text.
4. Land once C3's checks pass on the tree you push; Pascal authorizes syncing each verified batch to `origin/main` (C3). Other pushes need his request.

## Where code goes

- `src/gba/` is what any GBA decompilation could use: ELF and GNU ld map readers, a function's bounds, a source's recipe from its own Makefile (shell lines through the Makefile's SHELL), calcrom's count over a map, the Thumb reader, a C lexer, the process runner, the twins' shapes. It reaches nothing outside `crate::gba` and names no game, project or layout; the boundary test in `src/gba/mod.rs` refuses `crate::` paths out, `super::super`, the games' and project's names, and a project's folders and files (`out/`, `obj/`, `games/`, `recon/`, `roms/`, `rom.sha1`, `ld_script`, `objects.mk`, `deps.mk`, `resource_`, `_overlay`). A rule that is one project's (which folder is done, an overlay's sections, a placeholder's spelling it alone uses) is passed in by its caller.
- `src/alchemy/` is Alchemy's: rom.sha1's editions, the objects each edition links (`link`, from `out/<edition>/objects.mk`, which the Makefile writes from the linker script), the build's object folder (`built::object_stem` is its one reading), Camelot's overlays, DONE, humanity, and the tables of `evidence/` (H8), which `build.rs` compiles in.
- Each command's front-end is `src/<command>.rs`, or `src/<command>/` when it has parts; one command reaches another only through what it makes `pub(crate)` for that.

## Method

### Running the work

The main session ranks, briefs, verifies, adopts and lands; agents match. A workflow is one phase: read its results before starting the next. What took Alchemy's The Lost Age from 47% to 88% in a week:

1. **Rank before choosing.** The worklist comes from the tree by a command, never by hand: `rank` (with `--twins` for each piece's nearest matched function in the other game) lists every unfinished function in every edition, furthest first by skeleton gap (the instructions that differ once registers, stack offsets, pool offsets and branch distances are ignored), a function with no draft furthest of all, identical shapes grouped so one agent solves a family and its copies follow, and what does not measure last. Re-rank between rounds; a round takes the ranking's head and drops what the last round could not move, saying so. `where` (the bytes an edition still placed from `recon/`) and `editions` said where the bytes still to match were; with `recon/` gone, `editions` lists the objects one edition links and another does not. With nothing left to match, `twins GAME --all` (`--min N` for the shortest function read, 12 by default) pairs each function a game places from `games/` with the reference game's most like it, so a mechanism one game has humanized lends its names to the other's (H6).
2. **One agent per function or family, each editing only its own draft.** Nothing shared is edited in parallel: the linker scripts, headers, the Makefile. A type an agent needs goes in its draft. Agents never run make, never commit, never change git state, and keep scratch files in a folder of their own outside the repository; compiler dumps appearing in the repository root mean a brief forgot to say so.
3. **The brief is short and exact.** Name the rules that bite instead of pasting them; agents load this file and the project's `AGENTS.md`. Give the function, its draft and current figure, the exact measure command (rank's `measure` column: `diff` with nested listings, `--symbol`, `--edition`, `--arm`), the tools for the work (`diff --show`, `--hunks`, `--heat`, `--rtl`, `--alloc`, `--flag` for analysis; `variants` for named rewrites; `permute` for a search), the order of work (control flow and types, then allocation and scheduling, then tagged devices mildest first, only after reshaping fails), the stop rule (differ 0, or about twenty attempts in a row with no gain), keep-best (copy the draft whenever it improves, restore when an attempt goes backwards), the header to leave behind (`// Matches: differ 0 (edition, date)` or `// Draft, differ N of M (...)`, then what was tried), and the one file it may edit.
4. **Structured results.** Every agent returns a schema: status, differ in each edition, devices added and removed, what is left, and one new fact that reaches other drafts. The main session sorts and acts on data, not prose.
5. **Facts carry between rounds.** A final agent groups the round's new facts by reach and names the contradictions; the next round's briefs point at the result. Without it every round rediscovers the same compiler behaviour. A fact that holds across rounds belongs in "What matching has measured".
6. **Verify before adopting.** An independent, skeptical agent re-measures every claimed match in every edition (`diff --edition`) and reads it against the project's source rules: every device tagged, its measured N of M a row of `evidence/<game>-fakematch.tsv` (`check tags`, which still takes it from a tag that carries it), no disguised device, no assembly body, edition tests by the project's rule, no unevidenced name. Only confirmed matches go forward.
7. **Adopt serially, with the build as judge.** One owner adopted in batches, refusing a draft that did not measure differ 0 and holding a lock so no two adoptions met, then built every edition and traced a failure back to its function, which returned to its draft while the rest of the batch stayed. The draft forms went with `recon/`; `adopt merge` keeps the lock, the journal and the judging for gathering a game's objects into one in its linker script: `adopt --verify` builds every edition and sends back the merge that wrote the object placing the first differing byte, or by hand `make compare-editions`, `check rom` (the symbol and object that placed each differing byte, and the origin where a size change moved the layout), `check overlays`, `check packer`, and `adopt --undo JOURNAL ITEM`. A measured differ 0 is not a match: literal pool placement and padding, the next object's alignment, labels and nested functions, an edition's own bytes, and names the tables lack all show only in the linked ROM.
8. **Review, then fix forward.** An independent review of the landing range looks for what the build cannot see (untagged or disguised devices, edition names in C, unevidenced names, stale comments); `regress` against a saved `out/` classes every function a compiler, option or routing change moved. Fix, then land once C3's checks pass. Work that passes the checks is kept and landed; what a review finds is fixed in commits that follow, never by dropping or redoing the work (Pascal, 13 November 2026). Only a failed check (C3) stops a commit.
9. **Share the checkout by owner.** Concurrent workflows divide by what they edit: drafts, adopted source files, the toolkit. A binary in use is never rebuilt under a running workflow: change the toolkit in a worktree of its own.
10. **Tools live in this repository.** A script that ranks, adopts or measures becomes a command here the day it proves useful; scratch folders get wiped, and Alchemy lost its ranking and adoption scripts that way.
11. **Scale to the work.** Matching is wide: one agent per item over the whole ranking. Design questions are narrow: a few readers, then the main session decides. Never cap silently; log what a round left out (rank names the listings it leaves out on stderr). Check that an item list is not empty before launching it.

Near misses stopped by allocation or scheduling are not chased while far-off work remains; the far-off work often settles them. The last stretch works them with tagged devices where the project allows them, so DONE is reached and the devices are cleared afterwards: `sweep` takes out each device every edition compiles the same without.

Cost decides the shape. One agent per draft with a second agent verifying each claim cost about 64M tokens for 0.9 points of The Lost Age: most claims failed on rules the matching agent never checked. A few agents, each working a batch in turn and checking its own drafts against the rules (`check tags`, the source rules, `diff` in every edition) before calling one clean, took 2.75 points for 1.1M. Make the agent that writes a match prove it; keep independent verification for samples and landings.

### Humanizing a game

What "humanized" looks like was measured, on 13 November 2026, against pret's three GBA games and eight open-source GBA games people wrote. The portrait, with pokeemerald's numbers and where the two games stood that day:

| | pokeemerald | ☀️ | ⚓️ |
|---|---|---|---|
| Comment lines per 100 lines of C | 2.5 | 17.3 | 7.7 |
| Address-named identifiers | 1 | 1 | 3,554 |
| Hex literals per 1,000 lines | 24 | 6 | 106 |
| `goto` | about 60 | 307 | 1,721 |
| Number-plus-offset reads | 56 | 36 | 757 |
| PNGs named by number | 14 of 4,076 | 3,355 of 5,560, both games | |
| Fake matches | about 40 lines, `// Needed to match.` | 152 tags | 975 tags |
| Median lines in a `.c` file | 797 | 437 | 504 |

File sizes, the Makefile and the linker scripts were already pret's. What gave the games away was around the C: assets and maps named by number, thousands of small tables and assembly files, the reconstruction's evidence written into the code, and in ⚓️ placeholders, raw numbers and views.

Not to copy from hobby projects, because a 2001 commercial game with code overlays differs from them honestly: checked-in converted art, JSON data, a header beside every `.c`, files of two hundred lines (a scene is one overlay and one file), licence banners, the toolkit's stock linker script. The overlays' entry and import tables, the banks and `overlay.ld` are how the cartridge works: generate them, never hide them. `BUG`, `UB` and `UNUSED` marks are pret's own and stay.

How the work goes (Pascal, 13 November 2026: "big moves first, break things, fix later, never revert"; "one mechanical merge of the files into ROM stretches, and then fixing it bit by bit"):

1. **Big moves first.** A move is one mechanical change across a whole game: every neighbouring object joined, every scene one file, every import table generated, every map one text grid, every asset named. It is made in one pass and committed even while the build is broken. Details come after, never instead.
2. **Never revert.** A move that breaks the build is repaired in place: another natural way to write it, the right type or prototype, a helper Camelot likely had, a marked view where two parts disagree. A part is never split back out and a rewrite never returns to its old text. Earlier rounds joined files and then un-joined whatever resisted; that is what left ⚓️ at 519 C files when 430 were possible.
3. **Try before believing.** A limit is real only once the move was tried and the bytes refused. The shared field routines linked into the middle of ⚓️'s scenes "could not" be joined for a day, on an argument about optimisation levels nobody had tested; compiled inside the scene they gave the same bytes. A boundary the bytes do prove (German's text speeds, by alignment) is evidence of Camelot's own files and stays (Force the merge, below).
4. **Three passes over a lane.** Big moves, with the broken routines listed as they break; repair, forward only, until the lane matches; then a blind read by an agent that has not seen the history and may not look at it, who fixes what a person would not have written and gives a verdict for each folder. The blind read is the measure (H4); the counts are a worklist.
5. **Lanes by folder, one writer to a checkout.** Lanes run in worktrees of their own and touch only their folders. A rename of anything another lane uses is not made in the lane: it is a line in a shared `renames.tsv`, applied across the tree once at the join. A lane that renamed event commands in its own branch cost a merge with 261 conflicts and names that had silently swapped meaning.
6. **The join names what it merges.** It is told the exact branches and worktrees, merges nothing else, and no worktree it will read is reused while it is pending. One join merged two lanes that had been restarted in the same worktrees and were mid-rewrite.
7. **The brief opens with whose request this is.** It quotes Pascal's instruction and says that his other messages are separate matters. Agents shown a stray message of his ("we also have to clean up branches") as their request refused hours of work, three passes running, in two lanes.
8. **The gate that is trusted.** Before a commit that claims to match: delete `out/*/deps.mk`, `out/*/objects.mk` and the editions' `obj` folders (an incremental build keeps stale objects after a header change, and has reported both false failures and false passes), build every edition, run `make test`, build with a current GCC, and search for merge markers. Four guide pages reached the site with conflict markers in them because a merge's output was read by its last lines.
9. **Docs move with the code.** The READMEs under `games/` are pages of the site: a move that renames or removes a file corrects every page that names it in the same landing, and the site is built against the branch (no dead link) before it lands.

### Asking the compiler why

A fake match (S2) says what form the compiler needs, never why. The old GCC can say: it dumps its RTL after every pass (`-da`). Compile a function's kept form and its plain form and compare them pass by pass: the first pass where the difference stops being the device itself and becomes what reaches the assembly names the exact fact the device exists to produce (a value born before a call, a block boundary, a spill slot's order). That fact is the fingerprint of the original source, and the plain C that produces the same fact is the candidate for what Camelot wrote.

Reach for it when a tagged device has resisted reshaping, before adding a milder one or claiming a leftover, and when a family of tags may share one cause.

```sh
alchemy-devtools passdiff SOURCE.c PLAIN.c FUNCTION [--edition EDITION] [--object OBJECT.c]
```

`PLAIN.c` is a copy of `SOURCE.c` with the form written the plain way, as the tag's row of `evidence/<game>-fakematch.tsv` (or a tag that still carries it) says after `as`. The object that builds or includes `SOURCE.c` is compiled by the edition's own recipe (English by default) twice, in a linked copy of the game's sources, so nothing in the checkout changes. It prints a line per pass with the function's instruction count in each variant and how many lines of its RTL differ once insn and label numbers are set aside, then the RTL at the first pass that differs, then the assembly lines that differ. The dumps stay in `out/EDITION/obj/drafts/passdiff-FUNCTION`.

Pseudo-register numbers shift with any change of source, so every row differs by some lines and the count alone never names a pass: watch for the pass where the two instruction counts part, or where the RTL shows a new kind of fact. Read from the first differing pass onward. At `.rtl` the difference is usually the device itself; keep going until it changes kind: a register choice in `lreg` or `greg`, a block CSE ends early, an insn `sched2` will not move, a slot `reload` hands out in another order. That pass and that fact are the answer; the source shape that gives the same fact is then measured with `diff` in all six editions and judged by `make compare-editions`.

Over The Broken Seal's 166 fake matches (169 tagged; tbs-en unless six editions were checked; 12 November 2026) it gave twelve families by cause:

| family | cause | sign in the dumps | the source shape that answers it |
|---|---|---|---|
| 1. Not fake matches (7) | the ROM keeps the form's own instructions | the plain form deletes instructions the ROM has | `// DEAD:` or LEFTOVER under S2's physical test; one stale tag deleted |
| 2. Loop notes as a barrier (about 20) | an empty or once-only `do { } while (0)` leaves loop notes in the RTL | `sched2` does not move code across them, CSE ends its block there, `loop` places hoisted code by them | a statement macro, `do { <real statements> } while (0)` around its neighbours, at a family of five or more sites |
| 3. Constant born early, crossing calls (12) | the user pseudo is set before the first call | the constant lives in a callee-saved register across a `bl`; plain, it is born late or rematerialized | the value as a `static inline` parameter, which the inliner copies into a fresh pseudo at the head; fails where the ROM's value is born mid-function |
| 4. Pointer to a frame object born early (about 20) | `p = &local` is a low-numbered pseudo live across its uses | plain `&local` is CSE'd to `sfp+k` at each use, and allocation, spill slots and hoisting change | an inline helper whose first parameter is the pointer, doing all the work on it |
| 5. One variable for two lives (about 14) | one variable assigned twice is one allocno | its first life crosses calls, so the whole web takes a callee-saved register in `greg` | none plainer; very likely Camelot's own reuse, tagged `temporary` unless Pascal rules it the original's |
| 6. Spill-slot order (6) | `reload` hands out spill slots in pseudo-number order | one extra early pseudo swaps two slots; the code is otherwise the same | any real short-lived value at that point, such as a local initialised at its declaration |
| 7. Default placement (4) | the device is a local holding one constant | none needed: moved to its declaration, the form matches | `s32 width = 48;` at the declaration, six editions; whether that is S2's default or a temporary is Pascal's ruling |
| 8. CSE cannot see a value or an equality (about 25) | the device hides a copy, constant or branch equality from CSE, GCSE or combine | the first pass that differs is one of those three | no common source: each read on its own (an inline accessor, a work pointer read before a loop, a comma initialiser) |
| 9. A branch that dies late (about 12) | arms alike, or a body that empties late, keep a block boundary through `reload` or `sched2` | it merges only in `flow2` or `jump2`'s cross-jumping | none matched; likely a real two-way branch whose arms compile alike in this edition |
| 10. An equivalence note on a set-once constant (2) | local-alloc gives it `REG_EQUAL` or `REG_EQUIV` | its priority halves, or it is rematerialized | none found: the ROM's value was not a constant at expand |
| 11. The compiler, not the source (4, and a cluster) | `arm_reorg` counts an empty asm as 4 bytes; hard-register barriers; `sched2` ties | the pool break moves in `.mach`; ties in `sched2` | none in source; the pool case may be a K3 question for Pascal |
| 12. Frame layout of aggregates (3) | expand gives each declared aggregate its own slot | the frame size differs | one object of one shared type |

It cannot write the source: it names the fact, and the C that produces it is still found by hand and judged in all six editions. It compiles one edition and compares one function's RTL, so an inline or macro that moves a neighbour shows only in `diff` over the whole object and in `make compare-editions`. What happens before the first dump (parsing, inlining, expand) shows only as its result in `.rtl`. It cannot tell a device from the original's code (S2's physical test does) or decide a family bar or a ruling (Pascal does).

### Force the merge, then repair

Joining objects one pair at a time fails at every disagreement between their sources: a routine declared two ways, one struct name with different members, a macro defined differently. Pascal's idea turns that around: join everything at once and keep each disagreement, so the join cannot fail, then take away what turns out not to matter. What is left are the real disagreements, a worklist for humanizing.

Reach for it when a game's objects are to be gathered into the modules of their linker neighbours (S3's layout) and the sources were matched one by one.

```sh
alchemy-devtools adopt merge --keep-views --game GAME --verify
alchemy-devtools adopt settle --game GAME   # again until a pass deletes none
make compare-editions
```

`adopt merge --keep-views` joins every run of adjacent C objects on the game's route in one batch. Where a part sees a name otherwise than one before it, it keeps its own view under a private name bound to the same symbol, marked on the line above: `/* VIEW(PART): KIND NAME as THIS; OTHER has THAT. */`. The compiler judges every edition, function by function against the build's own assembly; a part nothing reconciles is left out, saying why. `adopt settle` then tries the true declaration or definition for each view and deletes every view that moves no code in any edition. It reaches a view wherever an object sees it: in the object, or in a file the object includes directly or through another (a part, a shared file scenes include as text, an internal header), the edit made in that file, its private name written plainly in every file of the object, and every object that includes a changed file compiled; objects that include one such file settle together. It reads a marker on one line or wrapped by clang-format over several. A view that stays ends its marker, written as clang-format wraps it, with what was tried and what it did: it does not compile (two parts wrote one thing two ways, settled only by understanding it, H2), or it compiles and moves N of M instructions (the disagreement shapes the bytes). `check tags` and `progress --humanity` count the views left. Last, a merged object is cut into parts, `<object>/<part>.c` included in ROM order from `<object>.c` with a private `<object>_internal.h` (S3); no command does the cut yet.

What it has measured, on The Lost Age (12 November 2026):

- The trial: 980 C files under `games/tla/src` became 468 (632 parts joined into 120 objects, 32 left out), keeping 1,935 views; settle deleted 1,225 and left 710: 565 do not compile with the other declaration, 85 compile but move code, 60 were not tried. The merge took about 6 minutes and the settle about 9; all twelve editions stayed byte-identical and the FAKEMATCH counts did not change.
- The run that followed, folder by folder: 339 parts joined into 71 objects (790 C files became 523), keeping 1,121 views; settle deleted 685 and left 436, and a second pass deleted none. The battle effects' three joined objects were then cut into 78 parts.
- What the views left say: the actor is typed five ways (about 165 views over four routines, most from one shared file that scenes include as text); one struct name carries different members in different parts (211 views over eight work areas); battle-object slots and a few globals have private types.

It joins only what the link order puts side by side: a shared object linked between two of a scene's files, assembly or picture data before a `.data` object, a file another includes and a file the Makefile names all keep a scene in several files. It does not settle a view whose definition holds a FAKEMATCH tag. The joined text is not readable until it is cut into parts, and a view is unfinished humanizing, never a solution.

A boundary the bytes show is evidence, not an obstacle (Pascal, 13 November 2026): where no single file could have produced the ROM's bytes, Camelot had more than one file there. The proven case is alignment: German's text speeds sit at an odd address before a pointer table, which one object's `.rodata` cannot do. A boundary is proven only by trying the join. The shared field routines linked into the middle of The Lost Age's scenes looked like one (built `-O2` in the main image, the scenes `-Os`), but compiled inside the scene at `-Os` they give the same bytes, so they proved nothing and the scenes were joined (13 November 2026). Such a boundary stays, is said in the first comment of the file it begins, and its files are named for what they hold, never for an address; it is counted apart from the splits that are only ours.

### What matching has measured

Facts about Alchemy's compiler, alchemy-gcc, not rules.

- `p[n]` and `*(p + n)` can compile differently; each site keeps the spelling it matches with.
- A struct declared before its type is complete keeps a smaller alignment: a header includes its structs' headers first. alchemy-gcc pads every struct to 4 bytes, so a table read by columns is a `[][N]` array.
- Locals declared in an inner block take their pseudos later and change allocation. Allocation order is r3, r2, r1, r0, ip, lr, r4 to r7, r8, r10, r9, r11; global.c ranks pseudos by refs over live length; a constant `REG_EQUAL` note doubles a pseudo's live length.
- A loop built from labels and `goto` has no loop notes, so loop.c and jump.c leave it alone; an empty C loop is deleted.
- An empty asm counts 4 bytes when literal pools are placed and emits none; a one-pass block's loop-end note ends CSE's block and is a scheduling barrier; sched2 breaks ties by RTL order. CSE reuses a register holding 0 or 1.
- A file that tests `LANGUAGE` without including `edition.h` silently gets the Japanese branch.
- Within an object, code and data follow definition order; only the linker script orders objects.
- Japanese is often an older layout of a function. A function that saves r9 and never uses it is a nested function storing its static chain.
- `-mtune=gba`'s multiplies `3 3` (K2), against `5 5`, bring 33 drafts closer and 1 further while every matched function still matches (8 November 2026).
- To measure a rewrite in seconds, compile its one object to assembly for one edition and diff it against the build's, `.L` numbers ignored; then `make compare-editions`.
- What took The Broken Seal's fake matches from 171 to 137 in one round (14 November 2026), each a cause written plainly, most used first:
  - A field read or stored through the type it really has (its true width and signedness), where a cast or a pointer stood in (6).
  - Spill-slot order: reload hands out stack slots in the order pseudos are made, and a local declared at the top of a function is made at entry. A stand-in pointer that existed only to give an address a lower number goes once the later locals are declared in the block where they begin. Its sign in `diff --show` is two or more spill-slot offsets swapped and nothing else (5).
  - A local set to its one constant where it is declared, and a pointer to a member with a `zero` local beside it both removed (5).
  - A once-only block that is a statement macro's own expansion: write the macro (`Io_Write8/16/32`, `Battle_SetRandomSeed`), four sites or more (4).
  - A loop that had been reduced by hand, written as the loop it is (4).
  - One object given one type where a union stood; one variable that was really two, split (4).
  - Argument order follows the callee's type: called through a type that returns a value, the second argument loads after the callee's address. Where the routine really leaves a value in r0, give it that return type; it is an honest type, not a costume (1, and the cause behind several earlier ones).
  - A stray `u8 *` puts a store in alias set 0 (may alias anything): remove it. Unions do the same and are the largest family still unexplained, with the block or loop boundary straight after a call.
  - Where the ROM keeps a test's own instructions, it is not a fake match but `// DEAD:` (S2's physical test).
- The system `make` on macOS is GNU Make 3.81, which compares file times to the second: a file rewritten in the second of its last build is taken as up to date, and incremental builds have both passed stale trees and failed good ones. Build with GNU Make 4 (`gmake`) or from deleted objects.
- An overlay's generated import table is rebuilt when the overlay's objects or its script change; before that fix an incremental build passed a compare a clean build refused.

## Rules

### Counting

These rules are about matching and counting; changing what they count needs Pascal and lands as its own commit (W6).

- **C1** A function counts only when its whole extent, literal pool included, compiles exactly and every edition stays byte-identical; in an edition, only when that edition links its C.
- **C2** DONE is pret's calcrom over the linker maps, by folder: bytes placed from `games/` are done, from `recon/` not yet. Code is `.text`; data is everything else. A game's figure sums its six editions.
- **C3** A landing is checked, not measured (Pascal, 12 November 2026): on the tree you push, `make compare-editions` prints OK for all twelve editions, `make modern` and `make test` pass, and so do this toolkit's own tests against that checkout (`cargo test --locked --workspace`, with and without `render`); CI rebuilds all twelve editions from a clean clone without a ROM and starts the docs build. The progress chart is a record, no longer updated; the report archive in the `decomp-reports` releases is kept as history and never deleted; nothing is sent to decomp.dev any more. Alchemy's `.github/publication.md` describes what CI does.
- **S4** Never throw work away: commit each adoption and attempt; a near miss stays a draft with its remaining difference in its header; an edition whose bytes differ stays on its scaffold and never blocks the others.

How Alchemy's matching ran, in its own words before `recon/` went:

- Match furthest first: drafts in `recon/<game>/en/main/<address>.c`; a near miss stays a draft with its remaining difference in its header (S4); a match is adopted into the module of its linker neighbours in every edition whose bytes agree, and committed (C1). A mismatch is fixed in source, or the code stays a draft (Alchemy O4). Anything that is not proven assembly (Alchemy S1) stays in `recon/` until it matches as C.
- ROM bytes reach the build only through pret's `.incbin "baserom.gba"` scaffold in `recon/`, which never counts (O1).
- "Not yet matched in this edition" is decided by the object list or the scaffold, never by a `LANGUAGE` test (Pascal, 7 November 2026; Alchemy S3).
- The Lost Age may add tagged devices to reach a match (S2).

### The oracle stays out of the build

The reference ROM judges the build and never feeds it. Reconstructing Camelot's compiler from habits across a whole game is allowed (K3); fitting a compiler, option or routing to particular functions is cheating.

- **O1** ROM bytes never reach the build, apart from the logo `ags-header` writes and the two exceptions A7 names. Nothing derived from the ROM steers the build or count.
- **O2** Every name is defined where its bytes are; layout is the linker script's order. No equate, alias or table gives a name an address, except Camelot's own fixed addresses (`FIXED_ADDRESS`), each listed once. An assembler equate holds only what its table computes or a value its evidence names; a size set only so the bytes come out right is a copied byte (S1); `.set` only switches assembly in or out.
- **O3** Scene, map and resource ids come only from their tables, used whole; overlay code never branches straight into the main image.
- **O4** A mismatch is fixed in source. Before a milestone, run an independent audit for leaks.
- **O5** Old git history, deleted files, backups and unreachable objects are never evidence.

### Source

S3, how the source is written, is in Alchemy's `AGENTS.md`.

- **S1** `games/` holds only real source: C from an approved compiler, or proven assembly written as instructions, never copied bytes. Assembly is proven as the compiler library, as 8-byte far-call veneers, or as handwritten code with an instruction, frame or pattern alchemy-gcc cannot emit, its `@ Why` saying which: rrx; a branch, adc or sbc on a shift's carry; r11 as an ordinary register; a callee save without lr; CPSR/SPSR; swi; computed pc into code; stores into code; unpaired multiply halves; a pc-relative block load of data; a mode switch inside a function; movs with no shift; ldm or stm writing back off sp other than a block copy from r0 or a doubleword pair; a conditional branch on flags with no compare; one literal pool shared by two functions; a linkage no procedure-call standard produces; or a copy the ROM keeps of a routine it also links, whose bytes are that routine's but for what a link fills in (pool words left 0, a call outside its library to itself) and whose calls keep that routine's offsets, or which stops short of its end (Pascal, 8 November 2026). Anything else is written as C. No C file places bytes through `asm()`.
- **S2** A fake match is what pret marks as one ("needed to match", "fakematch"): a line or form that does nothing for the program, or misstates it, and is there only so the compiler emits the original's code. One test decides it, whatever the form's shape (revised 11 November 2026 at Pascal's request): write it the plain way; if the bytes stay the same, the plain way is the source; if they change, ask whether a programmer would have written this for the program's sake. If not, it is a fake match and carries one tag inside its function: `/* FAKEMATCH(<kind>): the form kept; as <plain form>, N of M instructions differ in tbs-en. */`, N measured by a whole-function `alchemy-devtools diff`. The kinds, ranked by how far each misleads a reader, a modern compiler or someone changing the game, worst first (the ranking is ours; pret has none): `signature` (a type that is false: a return, parameter, declaration or local typed other than what it holds, a `const` left off, a call through a function type the callee does not have); `pin` (a variable fixed to a register); `barrier` (an empty asm, or an asm operand or clobber that does not say what the asm does); `wrapper` (a call layer that exists only for the compiler); `volatile` (the qualifier on anything but hardware or memory an interrupt shares); `temporary` (a copy of a parameter, global or local, a pointer standing in for a local's own address, or a local holding one constant or one pointer, where the plain expression compiles differently); `dead` (a store, read, test, arm or update that cannot change the result and for which the ROM keeps no instruction of its own: cancelling updates, self-assignments, never-true tests, both arms alike, a taken address, and a once-only block or loop, empty or round statements, that no macro expands to). Evidence (pokeemerald and pokefirered, finished; pokeruby and pmd-red, in progress; read 11 November 2026): the finished two have no register pin, no empty asm and no `NONMATCHING`, and mark as needed to match a parameter copied to a local, a pointer or unused local kept for the match, a variable reused, a self-assignment, `x *= 1`, an extern declared without its `const` and a header with a conflicting type; their only `volatile` locals are hardware's, their once-only blocks are macros', and their sixty-odd `goto`s carry no mark. So ☀️ takes no `signature`, `pin` or `barrier` (`make test` refuses the first two; the ten barriers left are to go), and a device is added only in place of a worse one. Replacing a device with milder ones is progress, however many it takes. A device comes only after reshaping has failed. Never patch compiler output.
  A leftover is Camelot's own code that does nothing in this edition and still shapes its bytes: the original's, not ours, and counted apart from the fake matches (Pascal, 12 November 2026). One physical test separates the original's code from a device (Pascal, 12 November 2026). Code whose own instructions are in the ROM is the original's: where it cannot change the result (a test never true, a store nothing reads, a read whose value goes unused, a call whose result is dropped, both arms alike, a self-assignment the ROM keeps as an instruction), it is written as the ROM has it and marked `// DEAD:` (S3), and leaving it out is not its plain way. A form that leaves no instruction of its own in the ROM and only changes how other code compiles (cancelling updates that fold away, an empty once-only block or loop, a copy that changes register choice) is a device, and FAKEMATCH unless evidence shows it is the original's leftover. A leftover keeps its form and carries one tag inside its function in place of FAKEMATCH: `/* LEFTOVER(<kind>): what remains and its evidence; as <plain form>, N of M instructions differ in tbs-en. */`, N measured as for FAKEMATCH. The kinds: `frame` (storage the ROM's own frame reserves and no instruction addresses, such as an unused local or an idle element of an array) and `template` (a shape copied from sibling routines that use it, idle here: a second blitter, a loop over one target, deltas recomputed after a swap). The frame is evidence (Pascal, 12 November 2026): this compiler reserves stack only for what its source declares and for spills, and a spill slot is used, so stack the ROM reserves and never touches can only be storage the original declared. An unused local that only sizes the frame is therefore LEFTOVER(frame) at any size, its tag stating the bytes reserved (`sub sp, #N`) and the ones no instruction addresses, as the function's assembly shows them, and any stronger evidence there is (`games/tbs/src/debug/test.c`'s buffer, filled by a loop only the Japanese edition keeps); storage an instruction addresses is no leftover. Any other leftover names its evidence: another edition, or the same routine in ⚓️, uses the thing (reads it, gives it a second value, runs its loop), and the tag names that edition or routine; the same shape repeats down sibling routines that use it, named; or a macro or helper reconstructed as below explains the rest of its family. ⚓️ counts only where its twin uses the thing, never where it merely needs the same form: a device ⚓️'s ROM also needs is one compiler meeting one reconstruction twice, not Camelot's (Pascal, 12 November 2026), and a form ⚓️ carries because H6 writes it from ☀️ says nothing. A leftover claim without its evidence is a device and stays FAKEMATCH, and so is any asm statement. When in doubt, it is a fake match.
  A macro or inline helper reconstructed from a family of sites is ordinary C only when the same ghost appears at four or more sites of the same kind of place (Pascal, 12 November 2026; two or three are a coincidence), one definition with the devices gone gives byte-identical code at every one of them in all six editions, its name says what its expansion does and never guesses the original's, and its `///` comment names the family and says the name is ours. A macro or helper below that bar, or one whose sites share nothing but the need to match, is a device in a costume and keeps its tag: wrapping a device removes no fake match. The count prints fake matches and leftovers on separate lines, each by kind, with the `// DEAD:` marks counted among the leftovers on a line of their own and never added to the fake matches; the fake matches are the number to drive to zero.
  Ordinary C, with no tag and only a short `//` note where the form would puzzle a reader: a default set where a local is declared or at the top of its function (`// Default:`; a whole routine has matched once its defaults were written in their order); `goto`; an equivalent spelling (`p[n]` or `*(p + n)`, `*&`, a cast that changes no type's meaning, a library routine called by name); an inline helper or a macro, with whatever its expansion holds, unless it stands where a device stood and falls below the family bar above; `volatile` on hardware; a local that holds a global or work pointer across calls (`struct BattleCamera *camera = gBattleCamera`) (12 November 2026); a local that names one constant and is initialised where it is declared (`s32 width = 48;`), as a programmer names a number for the program's sake, where one assigned later in the body stays a `temporary` (12 November 2026); one variable carrying two values in turn, Camelot's own habit (Pascal, 12 November 2026): pret's finished games mark a reused variable as needed to match, but here it is plain C by Pascal's ruling, since the reuse has no plain form that compiles the same and is how C89 code of the period was written; a range test wider than the loop that feeds it, a designer's frame window and a loop's length being two numbers tuned apart (12 November 2026); a layer that explains a habit of the whole game (`event.h`, `iwram_call.h`, `system_call.h`); the original's own undefined behaviour, kept behind `UBFIX` with a `// UB:` note (S3). `CAMELOT_ASM("proof")` marks the proven handwritten helpers inside C. A tag with no kind is unfinished: it is given its kind, or removed with its form, when its function is next touched.

### Compilers

The set is frozen: three C generators built from the pinned `alchemy-gcc` submodule (GNU's GCC snapshot of 2000-07-31, GNU's GCC 2.95.2 and pret's `old_agbcc`) with the parts the build never reads removed and host fixes that let them build and run on a current Mac and change no output. The snapshot also carries one code-generation change, `-mtune=gba` (K2); the rest is stock (Pascal, 8 November 2026). No new compiler, option, route or alchemy-gcc commit, except a host fix. Matching shows practical compatibility, not Camelot's exact compiler.

- **K1** Game Thumb C: alchemy-gcc (GCC of 2000-07-31) with `-O2 -mthumb -nostdinc -fcall-used-r4`, plus `-mthumb-interwork` for ☀️ and `-mtune=gba` for ⚓️ (K2). ⚓️'s C linked only into overlays takes `-Os` in place of `-O2`, a route by whole file and place in the build, never by function; its main image stays at `-O2`. libgcc with `-O2 -mthumb -mcpu=arm7tdmi -fno-inline`. ARM C: GCC 2.95.2 with `-O2 -mthumb-interwork -fomit-frame-pointer -fcall-used-r4`. Sound and flash: pret's `old_agbcc`. The Makefile's SOUND_C, FLASH_C and ARM_C are the only routes. What ☀️ routes through them, ⚓️ may route the same way, by whole file and by what the code is: ARM instructions, or the sound and flash libraries (Pascal, 5 November 2026).
- **K2** ⚓️ takes ☀️'s options without interworking, plus `-mtune=gba`. Options and tune are chosen by what the ROM and the hardware show, never by how much they match (Pascal, 8 November 2026): ⚓️'s 6,725 `pop {pc}` returns rule out interworking, which ☀️'s code never returns with. `-mtune=gba` is the ARM7TDMI tuned from GBATEK alone, as one engineer could have done it in a weekend in 2001: loads timed `3 2` (LDR 1S+1N+1I), stores `3 2` as loads, multiplies `3 3` (MUL 1S+mI, m = 2, an operand within 16 bits); without interworking, a call through a register is GBATEK's `mov lr, rN` and lone `bl` suffix instead of the `_call_via_rN` veneer; and a constant is built in its register instead of read from cartridge ROM, 255 below it first, else its low byte above a shifted byte. The 255-first order is read from the ROM: of its 13,828 split constants, the 4,017 where the two orders differ all take 255. The constant is built once, by the split pass after reload, and a constant move that first appears after it is left to the literal pool as stock GCC leaves it (Pascal, 11 November 2026). The ROM shows it at one site and nowhere against it: `Text_DrawPrefixedNumberAtOffset` stores the HP label's second tile in both branches in Japanese, English and German; `reload_cse_move2add` makes each `r3 += 1` and `r3 -= 1`, and cross-jumping, after the second scheduling pass, rewrites both as one load of `0xf01e` and merges them, which the ROM reads from its pool 90 bytes away where the two constants before it in the same function are built; of 35 other constants loaded after a join every one existed before the split and is built, and no other plain integer the tune builds is pooled at a word load's reach. With it that routine is one source in all six editions, ☀️'s too, and no other unit of either game compiles differently (about 4,490 units an edition, at `-O2` and `-Os`). Building constants at two moments, as alchemy-gcc did until then, was our doing; building them at one is the plainer engineering, and probably what a weekend's change would be: the tune as a whole is thin beside what GBATEK's timings would support, and is kept as Camelot's, not improved. Evidence (tla-en, 8 November 2026): against the C matched before, the tune differs in 805 functions where stock ARM7 tuning differs in 4,265; ☀️ under it differs in 3,314 of 7,715, so ☀️'s compiler had none of it. GBATEK's STR, 2N, alone gives stores `2 2`; `3 2` is read from the ROM by replaying 568 functions both games share by name and size, ☀️'s C compiled with ⚓️'s options and compared in shape with ⚓️'s ROM: `3 2` beats `2 2`, `2 1`, `3 1`, `3 3` and `4 2`, 245 twins exact against 236, and against `2 2` brings 53 closer and 8 further (8 November 2026). The twins cannot separate multiply timings (shared code has few multiplies); `3 3` is Pascal's reading of GBATEK (8 November 2026). An instruction-order mismatch alone is no reason to change compilers.
- **K3** A code-generation change needs evidence from the hardware or the ROM itself, never from how much C it matches; it lands in alchemy-gcc as its own commit with that evidence, recorded here, and with Pascal's approval. An option change needs one option set that explains most of a game's code, its evidence recorded here, and Pascal's approval.

### Humanizing

- **H1** The source reads as a GBA game a team wrote in C, and a reader learns how the game works from it. The bytes stay identical; nothing has to look like the original's own source, and our names are never presented as recovered. Where a choice is open, take what pret does (W3), then what a person writing the game would have done: fewer files, fewer lines, real names, tables as C, assets named for what they show.
- **H2** Understand a thing before naming or explaining it. Take one mechanism or one scene at a time: find out what it is (callers, data, the game's text, the running game), then type it, name it, shape it and explain it in comments and its page. A name or comment written before the thing is understood is redone. Work that needs no understanding may run across the tree: formatting, moving files, a literal replaced by the name it already has, a comment the code itself proves. Other names and comments may not.
- **H3** Names come from evidence: the game's text, its area names (`gArea_NameRules`), or what the player sees at the moment the code needs (right room, flags, leader, camera). The code's own words are a guess, never a name. Code nothing reaches has no render to name it from: its name says what its code does, confirmed by staging it (Pascal, 5 November 2026). Game terms are the English release's. What a name was taken from is written down (H8), a claim that someone looked, made only after looking, and removed when found untrue. Two walkthroughs may be read to find one's way, and no other outside writing about the games (Pascal, 13 November 2026): Telago's guides on GameFAQs, <https://gamefaqs.gamespot.com/gba/468548-golden-sun/faqs/39216> for ☀️ and <https://gamefaqs.gamespot.com/gba/561356-golden-sun-the-lost-age/faqs/44287> for ⚓️, kept in this repository's ignored `walkthroughs/` folder and never committed: read the Markdown (`telago-golden-sun.md`, `telago-golden-sun-the-lost-age.md`), a faithful reformat with a heading for every chapter and place and a table for every list, its words unchanged; the `.txt` beside each is the guide as downloaded. They are the first place to look for what a thing is: where it is, in what order events come, what the player does there. What the game names keeps the game's own word, found in its text; what the game leaves unnamed (a room, a puzzle, a step of an event) may be named for what the guide says the player sees there, once a render shows the same, and its evidence row cites the render. How the game works is read from the code, never from them.
- **H4** A unit is done when someone who has never seen it could follow it from its source and its page, and would take it for written code. That is judged by reading it cold (the blind read, in Humanizing a game), not by a list: start from what a reader cannot follow (a wall of bare numbers, a routine that says nothing of what the player sees), and no count that reads zero makes a unit done. What evidence could settle is settled; what it cannot stays a placeholder, or an open question as a `//` comment at the code: `XXX: <question>; <the evidence that would settle it>.` or `XXX (no evidence): <question>; <why nothing in reach settles it>.`, never on a page.
- **H5** `alchemy-devtools progress --humanity` is a worklist, not the definition; where a count asks for what these rules forbid, fix the count. A wrong name is fixed where it is; it becomes a rule only when it shows a principle these rules miss.
- **H6** ⚓️ is written as ☀️ expanded: where it keeps a routine, structure, mechanism, scene kind or habit ☀️ has, it takes ☀️'s names, words, layout and comments, changed only where its own code or evidence differs, and names afresh only what it adds (Pascal, 9 November 2026).
- **H7** The two games are evidence for each other. Where code is odd in both games at the same place, and ⚓️ there shows what explains it (a debug call or check, a macro's expansion, a helper, an extra argument), ☀️ had the same thing at that place, compiled away or empty: write ☀️ with that macro, helper or debug hook, named as ⚓️'s, and say at the code that the evidence is ⚓️'s. It runs both ways, and what one game's bytes prove of a file boundary (see Force the merge) is asked of the other's (Pascal, 13 November 2026).
- **H8** The evidence stays here, not in Alchemy's source (Pascal, 13 November 2026: "I don't like that star thing it's also in the docs. We have too many comments"). No `★ Named from` line is written: what a name was taken from is a row of this repository's `evidence/<game>-names.tsv` (name, kind of evidence, the evidence), and a fake match's measurement (what the plain form costs, in which editions) is a row of `evidence/<game>-fakematch.tsv` keyed by file and routine; the source keeps `FAKEMATCH(kind)` and a few words saying what the device is. Comments in Alchemy say what the game does, as a programmer on the team would have written them, at about the density pret's have (two or three lines in a hundred, where The Broken Seal had seventeen): a routine's brief stays, since the docs site prints it; narration of what the next line plainly does, and anything about the ROM, the compiler, addresses or matching outside the marks, goes.

### Documentation

The docs are the home page, the pages for what runs and what is shared, the folder READMEs, the glossary, the `///` comments and the site built from them (`alchemy-docs`). People read them; the two `AGENTS.md` files are the only ones written for agents. A unit's comments and page are written last, from what the earlier steps found.

- **D1** The docs are for a programmer opening this code for the first time, or one already in it looking for where something lives; nobody else reads them (Pascal, 12 November 2026). They explain how the game's systems work and how to think about them, a level above the code: not a modding manual, a wiki, a walkthrough or a how-to for changing the game, and nothing a comment in the source already says. A page gives the model of its subject, why it is built that way, and where its files are; field layouts, list sizes, row formats and which routine calls which are the source's to say.
- **D2** The docs are a tree that follows what runs, then the folders, each mechanism explained on exactly one page (D6) (Pascal, 12 November 2026). The home page (`games/tbs/README.md`) only orients: what is here, where to start, the map of the pages; it explains no mechanism. The main routine's page is the first chapter: one routine that runs four sequences in turn, each leaving in the main routine's work what runs next. Then a page for each sequence (the field, a battle, Lucky Dice, Lucky Wheels), a page for each thing every sequence shares (how code runs, which is waiting and tasks; windows and menus; sound; saving; game data; graphics; the Game Pak), and under those a detail page for one mechanism, which is its folder's README. A page has the sections its subject needs and no fixed set, and runs from a few hundred words to about a thousand. Each is written to a brief, kept out of the page, of what a reader should come away knowing, taken from the questions people arrive with (how is a new piece of state saved; what formats, colours and sizes can a picture have), and is judged by whether it answers them. A diagram shows the shape of the logic and nothing else: a box that needs a number, a field name or a condition to make sense belongs in the code, and a straight chain of boxes that only repeats one sentence is not a diagram; a reader who looked only at the diagrams, page by page, should come away with the right picture of the game. A section about something the player sees opens with its recording (D4). A table only where the values are the lesson, never a list of functions, files or an enum's numbers; one example where it makes a model click, never a walkthrough that teaches several mechanisms on the way through. The pages are rewritten to this shape from the home page down, one at a time; a page whose turn has not come keeps the form it has, and what it holds that no comment says moves into the source's comments before it is cut.
- **D3** Every place, person and event a page names is checked against the game's text and data and named as H3 names it; an internal number never stands in for a name.
- **D4** Pictures are the game itself: recordings and screenshots from `alchemy-devtools render` on a tbs-en build, published to the Blob store and referenced by their `https://alchemy.pascalpixel.com/` URL, with no text baked in. A recording is looked at before it is used: it must show what its name and caption say, and the checks that pass one prove only that pixels changed. Code the game never reaches is shown only staged by hand (`render guide --only unused`, one row a function), captioned as staged, never as how it "would play"; without a stage it has no recording (Pascal, 5 November 2026). A section about memory or timing has no recording. One that passes through a black screen shows at least ten seconds of the game before, between and after each (`render check` refuses otherwise). Small Mermaid diagrams, in the colours the docs already use and with the concept emoji (🏡 the field, ⚔️ a battle, 🎲 Lucky Dice, 🎰 Lucky Wheels, 🚩 a flag, 🎵 music, 📣 a sound effect), show a structure or order no recording can. Never a hand-drawn picture or a data dump.
- **D5** The docs are written by someone who loves this game, for a reader who does too (Pascal, 11 November 2026; `games/README.md` is his own and sets the voice). A page may greet the reader, say why a thing is worth their time and enjoy itself. Plain English a programmer who has never seen this code can follow, in short paragraphs of one thought each. Open on what the reader can see or do, and name the term after; give the reason right after the definition; choose one vivid example from the game over an inventory; say a claim once, in its plainest sentence; let a short sentence carry the news. A page that reads like a specification is redone. A programmer's own words (a loop, a pointer, a struct, a pixel, fixed point) need no explaining; the game's and the console's (a task, a sequence, an overlay, VBlank) are explained once, where they are first needed, or linked to the glossary. A page names a function or a file only where the reader will go and read it; which function calls which belongs to the source's comments. Enthusiasm is for the game and its engineering, and every fact stays exact. No retelling of the plot, and nothing about how the decompilation was made (a spelling kept for the compiler, the build's checks) beyond the introduction; `you` is the reader, the player is the player; headings name their subject or ask the reader's question.
- **D6** Say a thing once. Every mechanism, value, diagram and recording has one owning page, and every other page links there; a recording alone may open a section on each page that has one about it. What the project is, only in `games/README.md`; a sentence every site would repeat, once at the layer it describes. Before landing a docs batch, count the phrases, tables, diagrams and recordings it repeats across pages.
- **D7** A folder's README is its page; its `#` heading is unique. Link a glossary word at its first use, once. Where a word comes from is said only in the glossary's `Evidence:` lines and a folder's `## Evidence`, never in prose. Prose names the games, never ☀️ or ⚓️, and cites no rule of either `AGENTS.md`. A heading other pages link to is renamed only with those links. The site's settings live in `alchemy-docs`, never as markup in the source.
- **D8** A number is said by the name the code gives it and in the player's units; a number with no name gets one in the code first. Hex only as data a reader meets, in code formatting, as every symbol is. A cell behavior is said by what it does, never by its number.
- **D9** Comments say what the code cannot: what the player sees, units, why a forced form is forced, the evidence for a name. A comment the name or body already says is deleted. Declarations take `///` (a trailing `///<`), everything else `//`; a file opens with `/// @file`; no `@brief`; `@param` only where a parameter needs saying; the first sentence is the summary. FAKEMATCH tags, `// BUG:`, `// DEAD:` and comments inside functions stay `//`. An event's message call has the line it shows above it, quoted from the English text (`// "Is Jenna back yet?"`, a question with its `Yes:` and `No:` answers), wherever the event's message number is certain at that call; a quote is never guessed.

- **A7** Two kinds of bytes are known only by comparing with the ROM, and are kept as named, counted exceptions, the data's fake matches (the independent audit of 11 November 2026 raised them; Pascal left the ruling to the agents). ### Nothing but the source

The repository is a few short C files, pictures, music and tiny tools, as pret's are; caches, registries and scaffolding that make it look bigger than it is drift from the code.

- **N1** A tracked file under `games/` is read by the build or is a guide's Markdown.

- **N3** No registries kept by hand: a fact lives once, beside the thing it is about.
- **N4** No per-asset recipe files, stored offsets or sizes; one rule per kind of asset.
- **N5** No background files: notes and plans stay in the agent's scratch space.
